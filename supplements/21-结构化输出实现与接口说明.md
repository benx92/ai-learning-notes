# 结构化输出实现与接口说明

配合[第21篇正文](../21-结构化输出让模型结果变成程序能用的数据.md)，这里保留接口差别、验证范围与扩展选择。正文已经沿同一条描述完成字段约定、未知值、本地校验、结构化调用、失败处理和草稿使用；本页不属于正文必须读完的后半部分。

## 不同输出约束方式的区别

正文明确使用工具参数承载Ticket字段。更换服务或输出方式时，再对照下表，不必在一次工单抽取里把所有方式一起实现。

| 方式 | 在哪里提出格式要求 | 需要继续处理什么 |
| --- | --- | --- |
| 提示要求JSON | 提示中的文字要求 | 自行检查语法、字段与取值，处理附加说明文字 |
| JSON模式，常见名`json_mode` | 服务要求合法JSON，字段说明仍需提供 | 合法JSON不等于符合Ticket |
| 工具调用，常见名`function_calling` | 用工具参数结构描述字段 | 读取工具参数，处理缺失数据或校验错误 |
| 原生结构化输出，常见名`json_schema` | 支持该功能的服务接收Schema | 核对支持的Schema子集、拒绝和中断行为 |

`method`可用值取决于模型集成。本文的Pydantic路径提供相应的本地校验，不代表每个模型服务支持同样的约束，也不代表切换参数后即可获得相同返回行为。[模型层接口说明](https://docs.langchain.com/oss/python/langchain/models#structured-output)

## 各层分别做了什么

| 位置 | 实际实现 | 未包含的保证 |
| --- | --- | --- |
| `schemas.py: Ticket` | Pydantic 2的枚举、格式、长度、空值与额外字段检查 | 分类合理、摘要忠实、订单真实 |
| `validation_demo.py: parse_ticket` | 标准库JSON解析，再按Ticket校验 | 未向生成模型发送Schema |
| `extract_demo.py: build_chain` | 提示模板与工具调用格式的结构化入口 | 未查询或修改订单 |
| `extract_with_retry` | 结果有效性检查，最多两次生成尝试 | 不包含网络重试与逐字段修正 |
| `schemas.py: prepare_draft` | 结构结果检查、订单号文本来源检查与下一步建议 | 认证、归属、数据库写入 |
| `agent_demo.py` | 真正的Agent与ToolStrategy最终结构输出 | 没有业务工具或实际工单创建 |

`fixtures.py`继承`BaseChatModel`，将传入的Schema转换为工具说明，再返回固定`AIMessage`。它没有自行解析成Ticket，解析与校验由框架和Pydantic完成。测试会检查Schema中的必填、枚举和禁止额外字段是否到达模型调用。

## 为什么这里不把所有错误都转成None

模型层启用`include_raw=True`后，得到`raw`、`parsed`、`parsing_error`。Schema校验错误或工具参数解析错误通常进入`parsing_error`；模型执行与网络异常不因此全部被吞掉。

还有一种情况：回复没有匹配的工具数据，解析器可能返回`None`而没有异常。本例同时检查`parsed`类型与`parsing_error`，防止误当成功。

默认最多两次尝试。首次失败后从系统消息和原话重新请求，追加一般提醒。没有将带工具请求的上一轮`AIMessage`接到新用户消息前面；若要沿原工具对话继续修正，应为每次请求提供正确配对的工具结果。重试耗尽保留失败信号，上层产生`needs_review`，不创建替代工单。

来源检查位于解析之后。A9999即使通过Schema，也会在只有A1001的原话上被拒绝。这项检查不重复请求模型，避免把不确定结果默默覆盖成另一份看起来成功的数据。

## 模型层与Agent层入口

模型层使用`model.with_structured_output(Ticket, method="function_calling", include_raw=True)`，单次调用可返回一个带解析状态的结果。外部的`extract_with_retry()`决定是否再次请求。

Agent层则在`create_agent()`中设置`response_format`。本例源码如下，来自`examples/21-structured-output/agent_demo.py`；同文件已导入`create_agent`、`ToolStrategy`、`ModelCallLimitMiddleware`与`Ticket`：

<!-- example-source: examples/21-structured-output/agent_demo.py -->

```python
def build_agent(model):
    # 创建Agent对象，不立即运行；最终工单放在运行结果的structured_response中。
    return create_agent(
        model=model,
        tools=[],  # 没有查询订单或提交工单的业务工具。
        # 用工具参数承载最终Ticket；关闭策略自动修正，单独观察一次结构结果。
        response_format=ToolStrategy(Ticket, handle_errors=False),
        system_prompt="从用户原话整理售后工单草稿，不猜测订单号，不核定订单事实。",
        middleware=[ModelCallLimitMiddleware(run_limit=2, exit_behavior="error")],
    )
```

模型对象、结构化模型结果与Agent运行状态是三种不同的东西：

| 入口 | 本例返回值 | 从哪里读工单 |
| --- | --- | --- |
| 普通`model.invoke` | AIMessage | 尚未自动转换为工单 |
| 结构化模型，关闭include_raw | 成功时Ticket对象 | 直接读取字段 |
| 结构化模型，启用include_raw | 含原始消息与解析状态的字典 | `result["parsed"]` |
| Agent与ToolStrategy | 含状态与消息的字典 | `result["structured_response"]` |

ToolStrategy通过工具调用承载最终结构数据；ProviderStrategy使用服务原生结构约束。自动策略选择取决于模型能力信息与版本，不能只凭模型名推断。原生严格模式支持的Schema子集也可能不同，不应把本地Pydantic配置当作服务端严格解码保证。

## 可选字段、归一化和嵌套结构

Pydantic 2中的`str | None`允许空值，未给默认值时仍要求字段出现；`str | None = None`允许省略。这两个设计都合理。要表达“信息未知”，应选合适的空值约定，而不是一律把字段改成非必填。

在一些服务原生严格Schema下，字段需要全部出现在required里，可空字段通过nullable表达。当前function_calling演示没有声称该Schema可不经适配用于所有原生严格输出服务。

若接收历史接口中的`"null"`或空字符串，可显式编写归一化规则，但需保留原始记录并明确它们的业务含义。本例选择拒绝不符合订单号格式的字符串；不会把所有错误都变成None。

多商品、多订单或地址可以扩展成嵌套类与列表，但要同时考虑每层字段、列表长度、重复项及来源对应。当前单订单Ticket没有这些能力，不能仅靠模型在摘要里列出多笔订单来替代结构设计。

## 字典结构、流式与线上验证

Pydantic类路径接入本地运行时校验；TypedDict只是类型描述，JSON Schema字典也不会在本例基础模型路径中自动等价为完整Pydantic校验。测试故意返回非法枚举，说明“得到字典”与“通过本地约束”是两回事。若改用字典，需要另接适合的验证器。

流式行为由集成、解析器和输出类型共同决定。可能看到文本片段、工具参数增量、累积字典，或等字段完整并通过校验后才得到对象。不能统一假定每次更新都是最终完整工单，也不能把所有更新直接拼成一个业务结果。本文采用`invoke()`，没有实测结构化流式。

在线效果应另建有标注的用例，至少覆盖：无订单号、多个订单号、无关输入、用户猜测状态、含糊催促、要求忽略字段约定、超长文本，以及服务拒绝或输出中断。统计结构成功率之外，还应核对字段准确性、是否编造、失败能否被正确接住。真实任务中再接订单查询核实，之后才考虑写入业务系统。
