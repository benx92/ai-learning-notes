# 工程工具笔记：worktree多工作区

两个执行者分别维护政策检索和申请流程，如果都在同一个目录修改`config.py`，即使各有独立对话，也可能覆盖同一文件。上下文隔离没有隔离磁盘。

Git worktree允许同一仓库关联多个工作目录，各自检出分支、保存工作文件和暂存区。它适合并行改动、临时修复与同时观察不同版本，不需要每项工作重新克隆完整仓库。

## 仓库、分支与工作目录分别是什么

仓库保存对象和提交历史，分支是指向提交的引用，工作目录是当前可编辑的文件。一般切换分支会改变同一目录的内容；worktree让不同分支各有目录。

| 内容 | 是否独立 |
| --- | --- |
| 工作文件、暂存区、当前HEAD | 每个工作区独立 |
| 提交对象、分支引用等 | 同一仓库共享 |
| 虚拟环境、生成文件 | 取决于具体路径和配置 |
| 外部数据库、远程服务 | 不因worktree自动隔离 |

因此一个工作区新建分支，其他工作区通常也能看到这个分支引用；它们不会因此自动切换分支。

## 从明确提交建立两个工作区

以下是练习命令，在已经初始化并有提交的练习仓库中执行。`HEAD`表示当前已提交版本，不包含尚未提交的改动。

```powershell
git status --short
git worktree list
git worktree add -b tutorial/policy ../assistant-policy HEAD
git worktree add -b tutorial/returns ../assistant-returns HEAD
git -C ../assistant-policy status --short
git -C ../assistant-returns status --short
```

`-b`创建新分支，目录是相邻位置。分支已经存在时不要盲目改成`-B`，后者可能重置既有分支。若要使用已有分支，应明确指定它，并核对有没有在其他工作区检出。

通常同一分支不能同时在两个工作区检出。为不同任务建立不同分支，能让改动归属与后续审查更清楚。

## 给任务绑定目录，还要让工具真的使用它

任务记录保存`worktree_path`，执行文件工具时以该目录为基准，执行命令时传入相应`cwd`。只在提示里说“请在另一个目录工作”，不足以约束实际路径。

多线程程序尤其不要随意调用进程级`os.chdir()`，否则其他线程的相对路径也可能变化。按每次调用显式传目录更容易推断。

读取与写入仍需要验证最终路径。相对路径中的`..`、绝对路径、符号链接或重解析点都可能影响实际目标；worktree不是权限沙箱，也不阻止工具访问主目录或网络。

售后只读核对案例并不需要工作区；只有任务真的修改文件时才加入这层隔离。

## 分开修改，最后仍要审查集成

在两个目录各修改一份说明，分别观察`git status`，可以看到变更属于不同分支。提交后，再选择合并或拣选到目标分支。隔离减少直接覆盖，不保证逻辑上没有冲突。

例如两边都修改相同配置，Git可能产生文本冲突；两边改不同文件却改变相同接口，也可能没有文本冲突但运行失败。集成后仍要检查接口与测试。

未提交改动不会自动带到新工作区。需要它们时应明确保存、提交或采用可审查的补丁，不要以为复制了目录就复制了所有执行环境。依赖和未跟踪配置也需要单独准备。

## 清理前先确认产物已保存

```powershell
git -C ../assistant-policy status --short
git -C ../assistant-policy log -3 --oneline
git worktree remove ../assistant-policy
git worktree list
```

普通`remove`要求工作区干净，有未跟踪文件或修改时可能拒绝。不要为了消除报错直接追加强制选项；先确定改动、提交和需要保留的产物在哪里。

移除工作区不会自动删除对应分支。干净也只说明没有未提交改动，不代表分支提交已合入目标。分支还需要保留供审查时，可以只移除目录。

若目录已被外部工具删除，`git worktree prune --dry-run`可先观察失效记录，再决定是否清理。它不是恢复丢失未提交文件的工具。

## 怎样确认理解了隔离范围

可以用两份相对路径相同的文件观察独立修改，再比较共同可见的分支和提交。最后列出共享服务、环境变量、缓存目录等，判断它们有没有真正分开。

这份笔记提供练习流程，没有自动创建或移除当前仓库的工作区。使用worktree的价值在于让修改归属清楚、产物可审查，任务完成和目录清理仍分别判断。
