# 第18章：调用包装与拦截实验

三个独立实验只使用Python标准库，不调用真实模型或业务服务，也不创建退货申请。

建议配合[第18章正文](../../18-安全护栏与中间件不要让Agent乱跑.md)阅读：先看公共检查怎样包住调用，再区分中间件与业务后端，最后观察确认、重试和调用额度怎样影响执行。额度检查负责是否放行下一次调用，不判断业务目标是否完成。

```powershell
py -3.12 confirmation_demo.py
py -3.12 middleware_order_demo.py
py -3.12 call_control_demo.py
```

- `confirmation_demo.py`对应正文：未确认的请求只打印开始、结束与拒绝结果；确认分支才打印“进入业务函数”。布尔值由教学代码提供，实际确认必须读取受信任的记录。
- `middleware_order_demo.py`对应扩展说明：允许的查询执行，未知工具在业务函数之前被拒绝；外层日志保留两条路径。

`call_control_demo.py`另外演示两项独立实验：一次外部查询内部先超时再成功，实际尝试两次；模型替代函数被请求三次，但只执行两次，第三次直接返回超限。它没有实现Agent循环或组合预算系统。

限额计数在放行前增加，所以放行后抛错也消耗额度。计数只保存在闭包中，重新创建包装会清零；它不支持跨进程、持久累计或多线程并发保证。重试实验省略了等待，只用于观察调用次数。

正文实验中的`handler`是内部处理函数。确认失败时提前返回，因而不会调用它；确认通过才执行`handler(request)`。`with_trace(require_confirmation(submit_demo))`依次把确认层和日志层包在业务函数外面，外层日志也会记录拒绝路径。`finally`负责记录结束，不代表业务已经成功。

验证输出时，未确认分支应没有“进入业务函数”，已确认分支才有这行。这里的`confirmed`由实验代码固定提供，不能改成让模型传入布尔值为自己授权。

三个实验的检查目的不同，分别保留，不把它们当作完整LangChain中间件或持久审批系统。实际草稿确认、归属、过期和防重复逻辑见[第15章申请服务](../15-tool-calling/return_demo.py)。第19章的[Agent配置](../19-langchain/agent_demo.py)另有框架调用限额。
